## 1. Method and environment

- Real Chromium (`ms-playwright/chromium-1243`, headless) driven by Playwright from `/tmp/u04-browser-qa/*.mjs`; no repo file was used as a spec, config, or output target.
- Viewports rendered and inspected separately: desktop 1280×800, tablet 834×1112 (touch), mobile 390×844 (touch). Device scale factor 1 except where noted.
- All measurements are `getBoundingClientRect()` / `getComputedStyle()` values read from the live rendered page, plus full-viewport and full-page screenshots.
- Interactions performed per tier: load, read header/freshness/KPI/count, Make filter, Aging-only toggle, Sort change, reload persistence, pagination, filter-sheet open/close, vehicle detail open at every tier, current-action and history inspection, manager-action creation on an aging vehicle (`veh_001` BMW X5, 91 days), Escape close, focus-return check.
- State coverage: loading, results error, summary error (partial), empty (no-match), stale. Because MSW intercepts before the network, error/loading states were injected by wrapping `window.fetch` in an `addInitScript` and failing/delaying only `GET /vehicles` or `GET /inventory/summary` (a page-layer fault injection is the only reliable seam under a service-worker mock).
- 200% zoom was checked two ways: (a) device-metrics override to half the reference width with `deviceScaleFactor: 2` (a faithful browser-zoom proxy), and (b) root `font-size: 32px` (text-only resize). Width sweep 320/360/390/640/768/834/1024/1280 CSS px.
- Playwright's own suite was **not** run; this is exploratory browser evidence (Gate F) that complements, and does not replace, the deterministic E2E gate.

Screenshot index (`/tmp/u04-browser-qa/shots/`): `<tier>-01-load.png` (full page), `<tier>-01-viewport.png`, `desktop-02..06` (filter/sort/aging/pagination), `<tier>-10-detail.png`, `<tier>-11-after-escape.png`, `desktop-12..15` (detail → create action → escape), `<tier>-20/21-filter-sheet`, `desktop-30` loading, `desktop-31/32` errors, `desktop-33`/`mobile-33` empty, `<tier>-50/51-zoom200`, `desktop-95-sticky-header.png`, `tablet-96-chips.png`, `mobile-9x`, `desktop-99-history.png`.

## 3. Findings

### F-01 — Desktop first viewport shows almost no inventory; the inline filter panel spends vertical space it does not use horizontally
**Severity:** medium
**Requirement:** UI §6.1 (desktop reference composition / inline filter row), §4.5 (density changes by viewport), §12.1 (result field priority), §22 (reject "giant whitespace that reduces data density")
**Reproduction:** viewport 1280×800 → `http://localhost:3000/inventory` → load → measure the offset of the first result row.
**Observed:** header `y=32 h=74`; KPI section `y=138 h=91`; filter/discovery panel `y=261 h=272`; results section starts `y=565`; table starts `y=609`; first row `y=679`. Of 800 px of viewport height, only **1 row is fully visible and 1 partially** (row height 81 px). The filter panel consumes 272 px (34% of the viewport) while its fields occupy only ~540 px of the 1200 px content width (make x=57 w=152, min-age x=233 w=144, inventory-status x=409 w=185, max select width 185) — roughly 55% of that panel is empty horizontally, and the grid is two rows tall instead of the single inline row drawn in UI §6.1.
**Expected:** the desktop reference composition keeps quick controls + one line of filters so that the inventory table is the dominant first-viewport region; scarce vertical space should not be spent while horizontal space goes unused.
**Evidence:** `/tmp/u04-browser-qa/shots/desktop-01-viewport.png` (two rows visible), `/tmp/u04-browser-qa/metrics.json` (`desktop.density`, `desktop.kpis`, cell boxes), `/tmp/u04-browser-qa/misc.json` (`desktop.density`: `firstRowTop: 679`, `rowsFullyVisible: 1`, `rowsCrossingFold: 1`).

### F-02 — Tablet rows are taller than desktop rows; the "compact" table is not compact
**Severity:** medium
**Requirement:** UI §11.2 ("Compact inventory table. Lower-priority fields are hidden or condensed"), §12.1 (field priority), §4.5
**Reproduction:** viewport 834×1112 → `/inventory` → measure `table tbody tr` height.
**Observed:** tablet row height **97 px** (desktop 81 px) for a single record; 5 rows fully visible at 1112 px height. Causes: the CURRENT ACTION cell stacks `span.vehicle-table__current-action` (y=590 h=20) above a 44 px `Details` button (y=618, 62×44), and cells carry 12 px vertical padding while advertising a wide table (per-cell widths 166/104/131/115/260 over a 776 px table). VIN/STOCKED/STATUS are correctly dropped, but the height that is saved horizontally is partly re-spent vertically.
**Expected:** the compact tier should let a manager scan more records per screen than the full tier; the detail affordance should not add a second text line to every row.
**Evidence:** `/tmp/u04-browser-qa/shots/tablet-01-viewport.png` (5 rows in the first viewport, large gaps), `/tmp/u04-browser-qa/anatomy.json` (`tablet.rowAnatomy`: row `[29,578,776,97]`, button `[561,618,62,44]`), `/tmp/u04-browser-qa/metrics.json` (`tablet.table.rowHeights: [97,97,97,97,97]`).

### F-03 — "Aging only" quick control is below the 44 px touch minimum on tablet and mobile
**Severity:** medium
**Requirement:** UI §8 ("Touch-oriented interactive controls must target at least 44 × 44 CSS px…"), §11.2 (tablet touch targets), §11.3, §17.12
**Reproduction:** viewport 834×1112 and 390×844 → `/inventory` → measure `#inventory-aging-only` and `label[for="inventory-aging-only"]`.
**Observed:** tablet — input `[257,381,28,28]`, label text `[296,385,69,20]`, union of the two hit rects `108 × 28`. Mobile — input `[37,694,28,28]`, label `[76,698,69,20]`, union `108 × 28`. The control is 28 px tall, well below 44, and it is a first-class quick control that is available at both touch tiers (the adjacent Sort select is 188×44 / 324×44, the Filters button 68×44 / 324×44).
**Expected:** the visible control or its label must provide a ≥44 px tall hit area at touch tiers.
**Evidence:** `/tmp/u04-browser-qa/last.mjs` output (`agingOnlyInput`, `agingOnlyLabel`, `union {w:108,h:28}`), screenshot `/tmp/u04-browser-qa/shots/mobile-01-viewport.png` (checkbox next to "Aging only").

### F-04 — The vehicle detail drawer does not contain focus (modal focus escapes to the background page)
**Severity:** high (**Gate G / U05 overlap** — reported here because it was directly observable during the required focus checks)
**Requirement:** UI §17.8 ("Modal/sheet focus behavior does not strand focus on body"), §13.4 (focus trapped while modal behavior is active), §18 (focus model), UI §14 detail surface
**Reproduction:** viewport 1280×800 → `/inventory` → click `View details for BMW X5 (1HGCR2F83HA000001)` (drawer has `role="dialog" aria-modal="true"` + `vehicle-detail-scrim`) → focus `Close vehicle detail` → press Tab 7× ; then focus `Close` again and press Shift+Tab 3×.
**Observed:** forward — `button Close` → `select#create-action-status` → `textarea#create-action-note` → `button Record action` → **`body`** → **`select#inventory-sort`** → **`input#inventory-aging-only`** (all three outside the dialog). Backward — `Close` → **`button Next page`** → **`View details for Toyota Camry`** → **`View details for Toyota RAV4`**. The overlay is `aria-modal="true"` with a full-viewport scrim (`rgba(13,26,43,0.42)`, z-index 25), so keyboard focus is behind the overlay. The filter sheet, by contrast, **does** cycle correctly (12/12 Tab presses stayed inside `role="dialog" name="Inventory filters"`), so the two modal surfaces behave inconsistently.
**Expected:** while the drawer/sheet is modal, Tab and Shift+Tab cycle within it; focus must never activate the dimmed background, and it should never land on `body`.
**Evidence:** `/tmp/u04-browser-qa/final.json` (`desktop-detail-focus-trace`, `desktop-detail-focus-back`, `mobile-sheet-focus-trace`), `/tmp/u04-browser-qa/misc2.json` (`kbd-open.tabSequence`).

### F-05 — Tablet filter sheet: fixed 168 px group boxes with 65 px of content
**Severity:** medium
**Requirement:** UI §8 (spacing scale 4/8/12/16/24/32/48), §13.1/§13.4 (filter grouping and sheet), §22 (reject "arbitrary one-off spacing", "alignment")
**Reproduction:** viewport 834×1112 → `/inventory` → `Filters` → measure `.filter-group` and `.filter-group__fields`.
**Observed:** every group is exactly **168 px tall** (`fieldset.filter-group` y=491/676/860, h=168) while its content row is **65 px** (`filter-group__fields` y=517/701/885, h=65 - one 2-column row of the 44 px controls). Each group therefore carries ~86 px of dead space, visible as an uneven, non-scale gap between groups. Mobile does not show this (content 143 px in a 168 px box). Also inside the sheet, fields in the same visual column do not share a width: MAKE/MODEL selects are 387 px wide, while MIN/MAX AGE inputs are only **144 px** wide in the same 387 px column.
**Expected:** group containers size to their content, and fields in one column share one width so the sheet reads as a grid.
**Evidence:** `/tmp/u04-browser-qa/sheet-legend.json` (`tablet.groups`, `tablet.legends`), screenshot `/tmp/u04-browser-qa/shots/tablet-20-filter-sheet.png`.

### F-06 — "AGING" is printed twice, adjacently, wherever the aging condition is shown
**Severity:** low
**Requirement:** UI §12.2 (aging presentation), §9 (typography hierarchy, avoid redundant labels), §22 (polish)
**Reproduction:** viewport 390×844 → `/inventory` → first card (Audi Q7, aging); and each tier → open detail for `veh_001` → VEHICLE SUMMARY.
**Observed:** the rendered text of an aging record is `AGE / 151 days / AGING / • AGING` on mobile cards, and `INVENTORY AGE 91 days / AGING / • AGING` in the detail summary; i.e. the term `<dt>Aging</dt>` is immediately followed by the `aging-indicator` text `AGING`, so the same word appears twice with the dot. Non-aging records read `AGING / Not aging` and are unaffected.
**Expected:** one aging statement per region (e.g. `AGING · 151 days` or `Aging / Yes`), with the dot plus text retained for non-color-only meaning.
**Evidence:** `/tmp/u04-browser-qa/shots/mobile-card-aging-action.png`, `/tmp/u04-browser-qa/shots/desktop-10-detail.png`, `/tmp/u04-browser-qa/anatomy.json` (mobile card anatomy: `dt "Aging"` then `span.aging-indicator … AGING`).

### F-07 — "Has a manager action" and "No current action" are typographically identical in the results list
**Severity:** low
**Requirement:** UI §12.3 ("Current action may use a semantic chip plus supporting text. No current action must remain easy to scan because it is operationally important"), §5 ("A user should not need to open detail to know … whether a current manager action exists")
**Reproduction:** viewport 1280×800 → `/inventory` → compare row 1 (Audi Q7 — `Legacy Hold (Discontinued)`) with row 3 (BMW X5 — `No current action`).
**Observed:** both render `<span class="vehicle-table__current-action">` at `14px/400`, `rgb(13,26,43)`, transparent background, no marker of any kind; the only difference is the sentence. On tablet the same cell is `span.vehicle-table__current-action` `14px` above the Details button. With "Aging With Action 1" versus "Aging Vehicles 3", finding the two aging-without-action rows requires reading every row's text.
**Expected:** the no-action state should be scannable at a glance in a non-color-only way (neutral marker/label), while an existing action continues to be readable.
**Evidence:** `/tmp/u04-browser-qa/misc2.json` (`desktop-row-states`: identical computed styles + `actionHTML` for both rows), `/tmp/u04-browser-qa/shots/desktop-60-rows.png`.

### F-08 — The intended sticky result-table header never sticks, so 50 rows are scanned without column labels
**Severity:** low
**Requirement:** UI §12 (result contract), §21 ("table/card information priority", aging identifiable without hunting), §22 (scanability)
**Reproduction:** viewport 1280×800 → `/inventory` → `window.scrollTo(0, 1400)` → read `table thead th` position.
**Observed:** `th` computes `position: sticky; top: 0px`, but its scroll container `div.vehicle-table-scroll` has `overflow: auto` and height 4143 px (it grows with the table and never scrolls), so the sticky header sticks to a scrollport that does not move: at scrollY 1400 the header row's top is **-763 px** while the table still spans the viewport. Screenshot shows rows with no visible column headers. Same structure at tablet.
**Expected:** while the results region is being scanned, the column header row remains visible (the CSS intent), or the table is paginated/short enough that this does not matter.
**Evidence:** `/tmp/u04-browser-qa/shots/desktop-95-sticky-header.png`, `/tmp/u04-browser-qa/sticky.mjs` output (`ancestors` showing `div.vehicle-table-scroll overflow auto/auto h=4143`; `atScroll1400.thTop = -763`).

### F-09 — Horizontal overflow appears only below the WCAG reflow floor (195 CSS px)
**Severity:** low
**Requirement:** UI §11.3 ("No horizontal page overflow is permitted" — mobile), §21 ("text remains readable at browser zoom")
**Reproduction:** viewport 390×844 with device metrics overridden to width 195 / dsf 2 (≈ 200%+ browser zoom) → `/inventory` → `documentElement.scrollWidth`.
**Observed:** `innerWidth 195`, `documentElement.scrollWidth 216` (+21 px). Offending elements: the three `div.kpi-card` boxes, each a fixed **200 px** wide at x=16. No overflow at 320, 360, 390, 640, 768, 834, 1024, 1280 CSS px, and none at root `font-size: 32px` (200% text) at any reference tier (desktop 1280→1280, tablet 834→834, mobile 390→390).
**Expected:** no horizontal page scroll; a KPI card should be `width: 100%`/`max-width` driven rather than a fixed 200 px so it survives sub-minimum widths.
**Evidence:** `/tmp/u04-browser-qa/misc2.json` (`zoom195`), `/tmp/u04-browser-qa/overflow.json` (0 offenders at 320/360/390/640/768/834/1024/1280), `/tmp/u04-browser-qa/rm.mjs` output (`overflowAfter` unchanged at all tiers).

## 4. Explicitly verified as good (non-findings)

1. **URL-owned collection state.** Make → `/inventory?make=BMW`; Aging only → `?make=BMW&agingOnly=true`; Sort → `&sort=inventoryAgeDays%3Aasc`; after a hard reload the controls re-hydrate (`make=BMW`, `agingOnly=true`, `sort=inventoryAgeDays:asc`) and the results stay filtered (count `1 of 1`). Filter change resets to page 1.
2. **Tier presentation models are genuinely different.** Desktop = real `<table class="vehicle-table--full">` + inline filters + right drawer (`544×800`, x=736, radius 0, shadow `rgba(13,26,43,0.22) 0 12px 40px`) with inventory context visible beside it; tablet = `vehicle-table--compact` + filter sheet (bottom sheet `834×705`, top-only 10 px radius) + wide centered sheet detail (`767×1001`, 10 px radius, background context visible); mobile = `ul.vehicle-cards` of 50 `<article>` cards (no `<table>` in the DOM) + full-width sheet (`390×705`) + full-screen detail (`390×844`, radius 0, no shadow).
3. **Manager journey.** Creating a `Wholesale / Auction` action on aging `veh_001` updated CURRENT ACTION (status, `ACTOR Alex Manager`, `RECORDED 2026-09-11 12:16 UTC`, note) and appended ACTION HISTORY; two successive actions rendered newest-first. Pending state: submit `disabled`, `aria-busy="true"`, label `Recording action…`, list of 50 rows still rendered, no modal confirmation. Persistence key `keyloop:mock:vehicle-actions:v1` updated.
4. **Close/focus return.** Escape closed the drawer/sheet every time (`[role=dialog]` count 0) and focus returned to the originating `data-vehicle-detail-trigger="veh_001"` button, for pointer-opened and keyboard-opened detail alike; the sheet closed by Escape, by `Done`, and by `Close`, restoring focus to the `Filters` trigger (`aria-expanded="false"`).
5. **No unintended horizontal overflow at any reference tier** (1280/834/390) and at 320/360/640/768/1024, and none under 200% text resize.
6. **Status semantics are not color-only.** Aging = amber `#92400E` text + 8 px dot (dot `aria-hidden`, word "AGING" present); not-aging = the words "Not aging"; lifecycle (`AVAILABLE`/`RESERVED`/`UNAVAILABLE`) and action status are plain text; staleness is a sentence, not a color.
7. **Loading / empty / error / stale are contextual.** Loading = 11 skeleton nodes across header/KPI/list with `aria-busy="true"` and no fabricated counts; empty = "No vehicles match the current filters." with `0 of 0 vehicles`; results error = regional banner + `Retry` while KPIs, freshness and filter shell remain; summary error = KPI-region error while the list still loads (true regional failure isolation); stale = header timestamp + warning sentence, inventory retained.
8. **Hover / focus / pressed states exist and are measurably distinct.** Row hover `rgba(0,0,0,0) → rgb(234,240,248)` (desktop + tablet); Details button hover `rgb(255,255,255) → rgb(234,240,248)`; pressed adds `translateY(1px)` and a darker fill; primary button `#1D4ED8 → #1E40AF → #1E3A8A`; focus ring `2px solid rgb(37,99,235)` (offset 2 px on the primary button) on every control in the tab order, including inside the zoomed state.
9. **Reduced motion respected.** `transitionDuration` `0.12s → 1e-06s` under `prefers-reduced-motion: reduce` at all three tiers.
10. **Design-system consistency / not a template.** Radii are exactly 0 / 8 px (controls) / 10 px (panels, sheets) / 999 px (pills); no gradients anywhere (`backgroundImage` "none" for every element); no resting-state box shadows (elevation only on the drawer/sheet/scrim); surface palette limited to white, `rgb(238,242,248)` muted, `rgb(255,247,237)` amber status, plus the amber dot. Tabular-numeric KPI numerals at 32 px with 26 px page title, 14/13/12 px dense body — a restrained, non-templated operational look consistent with UI §7.
11. **Mobile card priority matches UI §11.3.** Order is make/model → Age (151 days) → Aging (dot + text) → Status → Current action → full-width `Details` (324×44); VIN is demoted to 12 px muted text in the card header.
12. **Pagination** present and functional at all tiers (`Page 1 of 2`, `55 vehicles`, `Previous` disabled/`Next` enabled); mobile page 2 → `?page=2` with 5 cards and count `5 of 55 vehicles`.

**Observations that are not findings (recorded for reconciliation):**

- `Clear all` removes collection filters (`make`, `agingOnly`) but keeps `sort=inventoryAgeDays:asc` in the URL. UI §13.3 says it "removes collection filters and returns to the default collection state"; sort is grouped with the quick controls (§13.1) rather than with the filters, so this is defensible — flagging only in case U06 wants it decided explicitly.
- KPI values stay collection-wide (`55 / 3 / 1`) while the result set is filtered (`1 of 1`). UI §10 does not require filter-scoped KPIs; noted only because the two numbers sit close together on screen.
- Desktop `Details` buttons are 62×28 (below 44 px); UI §8 exempts "a dense desktop-only table … with an equivalent accessible target", and the same control is 62×44 on tablet, so this is accepted as-is.
- The desktop drawer's `Record action` button is 119×36 (desktop pointer only); it is 44 px tall at both touch tiers.

## 6. Limitations

- All data comes from the MSW browser mock; no real backend, network latency profile, or production data volume was exercised (the fixture is 55 vehicles / 2 pages).
- Loading and error states required page-layer `fetch` injection because MSW answers inside the service worker; the presentation verified is the application's own state UI, but the trigger is synthetic.
- 200% zoom was approximated with a device-metrics override plus a root font-size resize rather than a literal browser zoom control; the width sweep 320–1280 px bounds the result.
- F-04 is a Gate G (accessibility) class defect; U05's accessibility audit owns the authoritative verdict and should re-derive it independently.
- Exploratory browser evidence only. It complements and does not replace `npm run test:e2e`.
