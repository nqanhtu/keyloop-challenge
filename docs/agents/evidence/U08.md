## 6. Judgement on the accepted residual (desktop first-viewport density)

The residual Codex Lead accepted — "at 1280×800 the desktop first viewport shows two fully visible result rows and the results region is a bounded scroll region showing five rows at once" — reproduced **exactly** in this audit: first row `top=605`, row height 84 px, `rowsFullyVisibleInViewport = 2`, `rowsCrossingFold = 1`, results region `544 px` (`min(68vh, 44rem)`) containing 5 fully visible rows, and the page itself only scrolls 410 px.

Judgement against the four sections named:

- **UI §4.5** ("Desktop may be information-dense…") is permissive, not a row-count mandate; the desktop tier is genuinely the densest of the three (8 columns, 84 px rows, 87 % filter-row utilisation).
- **UI §6.1** draws a composition of header → KPI row → quick controls → filter row → results (+count) → pagination. All six bands exist, in order, and the results band plus pagination sit exactly where the drawing places them. Nothing in §6.1 fixes how many rows must fit in the first 800 px.
- **UI §12.1** is a *field-priority* contract, and it is satisfied at every tier (desktop shows all eight priority fields; tablet condenses VIN/Stocked as "condensed/visible" allows; mobile keeps every priority fact in the card `dl`).
- **UI §22** rejects "giant whitespace that reduces data density" and "arbitrary one-off spacing". The U04 F-01 half-empty filter panel was repaired: the panel is now 198 px (was 272 px), the filter row uses 1014 of 1166 px (87 %), and the tablet sheet's 86 px dead space is now a 25 px legend gap.

The bounded scroll region is also what makes the sticky column header work (U04 F-08): after `region.scrollTop = 1200` the `th` row sits at region-top + 4 px, and wheel scrolling inside the region moves the region while the page stays at `scrollY 0`. Bounding the region is therefore the mechanism that repaired a separate U04 defect rather than accidental whitespace.

Conclusion: the residual is a **deliberate, evidenced trade-off that does not violate any MUST-level statement in UI §4.5, §6.1, §12.1 or §22**, so the affected requirements are marked PASS with the residual recorded here. For completeness the same reasoning applies to the mobile first viewport (results section starts at `y=829` of an 844 px fold, so the "Inventory" heading is visible but the first card begins 25 px below the fold): UI §11.3 and §21 specify card priority order and content, which are satisfied, and no MUST-level statement requires card pixels in the first viewport.

## 7. Other recorded observations (non-blocking, no verdict change)

1. The aging legend is hard-coded prose in the dashboard ("Aging inventory is 91 or more days in stock", `inventory-dashboard.tsx:310`). It is explanatory copy, not a computation — no aging is recomputed — but the sentence duplicates the backend threshold and would drift if `--policy` aging ever changes.
2. `Clear all` keeps `sort` when it is present (sort is grouped with quick controls in UI §13.1). Consistent with the U04 note; `clearAllFilters` resets page and collection filters and keeps `vehicleId`.
3. Business-rejection association is form-level (`aria-describedby` on `<form>`), which matches the vehicle-level rule; `#create-action-status` itself has no `aria-invalid`.
4. Desktop `Record action` is 119×36 px and desktop table `Details` is 62×28 px — both above the mechanically enforced 24 px floor and on a pointer-only tier (Lead ruling Q3); all touch-tier equivalents are ≥44 px.
5. While any modal is open the background is `inert` and scrim-covered, so `Clear all` (and any other background control) is unreachable by pointer or keyboard until the modal closes. This is the intended modal contract (UI §13.4/§17.8) and the `Clear all`-preserves-detail guarantee is therefore exercised at the state layer (`clear-all-detail.test.tsx`).
6. `sort`/`page`/filters remain collection-wide while KPIs are collection-wide too (`55 / 3 / 1` next to `1 of 1` when filtered). UI §10 does not require filter-scoped KPIs.
