# Accessibility Audit - Keyloop Intelligent Inventory Dashboard

Independent, repository-mutation read-only audit (Gate G - Accessibility Proof).
The auditor did not write this code and modified nothing in the repository.

## 1. Environment and method

| Item | Value |
|---|---|
| Repository | /Users/tunguyen/Projects/keyloop-challenge |
| Branch / HEAD | main @ 043069e (merge: integrate U03 visual redesign) |
| App | npm run dev (Vite 8.3.0), http://localhost:3000/inventory |
| Browser | Chromium 153.0.8010.12 via Playwright 1.63.0 (real browser + real keyboard) |
| Viewports | desktop 1280x800, tablet 834x1112, mobile 390x844 |
| Scratch | config/specs in /tmp/u05-a11y/specs, raw data in /tmp/u05-a11y/out, screenshots in /tmp/u05-a11y/shots |
| Authority | UI System Design sections 11-19 (accessibility contract 17, focus model 18, motion 19); System Design 6.10; QUALITY_AND_LEARNING Gate G; skill .agents/skills/check-fix-accessibility |

Method: real Chromium driven by Playwright specs that emulate keyboard-only input
(Tab / Shift+Tab / Enter / Escape), read the rendered getComputedStyle colour,
the effective background (composited through translucent ancestors), font metrics
and getBoundingClientRect, and walk the live tab order against the open
[role="dialog"]. Contrast ratios use the WCAG 2.x relative-luminance formula;
thresholds applied are 4.5:1 normal text, 3:1 large text and 3:1 non-text.

## 2. Verdict

The dashboard does NOT fully satisfy the UI System Design accessibility contract
(Gate G: FAIL). Two defects are release-blocking, because Gate G states that no
unresolved critical/high accessibility finding may remain:

- F1 - the vehicle detail modal does not contain keyboard focus, and its aria-modal
  background stays interactive, reachable and exposed to assistive technology;
- F2 - the shared muted text token fails WCAG AA contrast everywhere it is used.

Three further defects are non-blocking but should be fixed (F3-F5). Everything else
in the contract reproduced as good (section 4).

Release recommendation: do not release as-is. Fix F1 and F2, then re-run this proof.

## 3. Defects

### F1 - Vehicle detail modal does not trap focus; background stays reachable, exposed and scrollable

- Severity: high (Gate G release blocker)
- WCAG: 2.4.3 Focus Order (A); 4.1.2 Name, Role, Value (A) - the aria-modal="true"
  contract is violated. Supporting: 2.4.7 Focus Visible (A) for the mobile case.
- UI System Design: 17.6, 17.7, 17.8 ("Modal/sheet focus behavior does not strand
  focus on body"), 18 (focus and keyboard model), 14 (vehicle detail surface).
- Reproduction (desktop 1280x800): open /inventory, Tab until
  "View details for BMW X5 (1HGCR2F83HA000001)" is focused, press Enter, then press
  Shift+Tab once.
- Observed:
  - Shift+Tab from the entry point immediately moves focus to
    button[aria-label="Next page"] - a background pagination control outside
    [role="dialog"]. The same first-step escape happens at tablet (834) and mobile (390).
  - From the entry Close control, Tab x4 lands on document.body; focus is stranded
    off the dialog.
  - The background is not inert: [inert] element count = 0, document.body is not
    inert, #inventory-sort and the table are not aria-hidden, and 57-62 background
    controls remain focusable while aria-modal="true". Programmatic focus of
    #inventory-sort while the modal is open succeeds.
  - Desktop: the background page still scrolls behind the open drawer (window.scrollY
    moved 0 -> 800 on wheel).
- Expected: while the detail drawer/sheet/fullscreen is open, keyboard focus stays
  inside the dialog (first/last control wrap), background content is inert or
  aria-hidden, and background scroll does not move the page underneath. Closing
  restores focus to the originating trigger (that part does work - see 4.3).
- Impact: a keyboard user tabbing past the form silently leaves the modal into hidden
  or partly covered content; a screen-reader user is told the dialog is modal while AT
  can still reach the page behind it. On mobile the detail is full-screen, so the
  escape target is not visible at all (focus is effectively lost).
- Evidence: out/detail-focus-containment-desktop.json,
  out/detail-focus-containment-tablet.json, out/detail-focus-containment-mobile.json,
  out/detail-at-exposure-desktop.json, out/detail-at-exposure-tablet.json,
  out/detail-at-exposure-mobile.json, out/detail-scroll-desktop.json,
  shots/detail-focus-containment-desktop.png, shots/detail-entry-desktop.png.

### F2 - Muted text token fails WCAG AA contrast (4.36:1 / 3.88:1 vs 4.5:1)

- Severity: high (Gate G release blocker; systematic, many visible elements)
- WCAG: 1.4.3 Contrast (Minimum) (AA)
- UI System Design: 17.11; token defined in section 8
  (--ui-text-muted: #6b7a90, i.e. rgb(107,122,144)).
- Reproduction: open /inventory at any tier. Values below are read from the rendered
  DOM, not from the stylesheet.
- Observed (measured ratio vs 4.5:1 required; every use is 12-13 px, never large text):

| Element | Foreground | Background | Ratio |
|---|---|---|---|
| KPI card labels (TOTAL INVENTORY, ...) 12px/600 | rgb(107,122,144) | #ffffff | 4.36 |
| Toolbar label SORT 12px/600 | rgb(107,122,144) | #ffffff | 4.36 |
| Filter labels (Make/Model/Min/Max/Status) 12px/600 | rgb(107,122,144) | #ffffff | 4.36 |
| Filter legends (Vehicle / Inventory age / Status) 12px/600 | rgb(107,122,144) | #ffffff | 4.36 |
| Table header cells 12px/600 | rgb(107,122,144) | #eef2f8 | 3.88 |
| Detail section headings 12px/600 | rgb(107,122,144) | #ffffff | 4.36 |
| Detail fact labels (VEHICLE, VIN, AGING, ...) 12px/600 | rgb(107,122,144) | #ffffff | 4.36 |
| Detail form labels (Action status, Note) 12px/600 | rgb(107,122,144) | #ffffff | 4.36 |
| Mobile card VIN 12px/400 | rgb(107,122,144) | #ffffff | 4.36 |
| Mobile card detail labels 12px/600 | rgb(107,122,144) | #ffffff | 4.36 |

  For reference the same token is 4.14:1 on the page canvas #f7f9fc; the table-header
  case (3.88:1) is worst because muted-on-muted composes two low-contrast surfaces.
- Expected: at least 4.5:1 for all of the above (none qualifies as large text), or
  3:1 only where the text is large. A darker muted token, or a lighter table-header
  surface, removes this whole class of failures.
- Impact: the small uppercase labels that carry the dashboard's structure (filters,
  column headers, detail field names) are hard to read for low-vision users at every tier.
- Evidence: out/contrast-dashboard-desktop.json, out/contrast-dashboard-tablet.json,
  out/contrast-dashboard-mobile.json, out/contrast-detail-desktop.json,
  out/contrast-detail-tablet.json, out/contrast-detail-mobile.json,
  out/contrast2-390.json, out/contrast2-1280.json, shots/semantics-desktop.png.

### F3 - Aging only toggle is below the 44x44 touch target at tablet and mobile

- Severity: medium
- WCAG: 2.5.8 Target Size (Minimum) AA - the 24x24 floor is met; the UI System Design
  44x44 requirement is not.
- UI System Design: 11.2 (tablet: "Touch targets follow the 44px minimum"), 11.3
  (mobile), 17.12 ("Touch-oriented controls meet the 44 x 44 CSS px target").
- Reproduction: open /inventory at 834x1112 and at 390x844; inspect
  input#inventory-aging-only.
- Observed: rendered box 28x28 CSS px at both touch tiers (24x24 at desktop), while the
  enclosing .toolbar-field--toggle row is 40 px tall. The associated label ("Aging only",
  69.42x20.3) is clickable and enlarges the effective hit area (row 324x40 mobile,
  112x40 tablet), so WCAG 2.5.8 passes; the 44 px design target does not.
- Expected: the toggle control's own box is at least 44x44 (or the whole toggle row is
  at least 44 px high) at the tablet and mobile tiers.
- Note on the repository gate: e2e/accessibility.spec.ts asserts only the 24 px floor
  (MIN_TARGET_SIZE = 24), which passes. Every other interactive control measures at
  least 44x44 at tablet/mobile (out/targets-tablet.json, out/targets-mobile.json), so
  this is the only 44 px gap.
- Evidence: out/targets-tablet.json, out/targets-mobile.json, out/aging-toggle-tablet.json,
  out/aging-toggle-mobile.json, shots/aging-toggle-mobile.png.

### F4 - Dashboard route renders no main landmark (and no skip link)

- Severity: medium
- WCAG: 1.3.1 Info and Relationships (A); 2.4.1 Bypass Blocks (A - limited here because
  there is no repeated navigation block, but the landmark is still missing).
- UI System Design: 17 (accessibility contract intent), 20 (component hierarchy).
- Reproduction: open /inventory; evaluate
  document.querySelectorAll('main, [role="main"]').length.
- Observed: main landmark count = 0 on /inventory (h1 = 1, lang="en", title present).
  Pagination is correctly exposed as nav aria-label="Inventory pagination", so AT users
  can jump to navigation but have no main region. The / index route does use main; the
  dashboard does not.
- Expected: the dashboard is wrapped in a single main (or role="main"), optionally with
  a "Skip to main content" link.
- Evidence: out/landmarks.json, out/semantics-desktop.json, out/semantics-tablet.json,
  out/semantics-mobile.json.

### F5 - Filter sheet background is not inert while aria-modal="true"

- Severity: low
- WCAG: 4.1.2 Name, Role, Value (A) - partial aria-modal contract gap.
- UI System Design: 13.4 ("Focus is trapped only while modal behavior is active" - this
  half is satisfied).
- Reproduction: open /inventory at 834x1112 or 390x844, tap Filters.
- Observed: focus is trapped (no Tab/Shift+Tab escape across 40 forward and 40 backward
  presses), but [inert] count = 0, document.body is not inert, and #inventory-sort is
  neither inert nor aria-hidden, so programmatic focus and AT traversal of the
  background still succeed while the sheet declares itself modal.
- Expected: while the sheet is modal, the background is inert or aria-hidden (not merely
  keyboard-intercepted).
- Evidence: out/filter-sheet-inert-tablet.json, out/filter-sheet-inert-mobile.json,
  out/filter-sheet-tablet.json, out/filter-sheet-mobile.json.

## 4. Verified-good results

### 4.1 Keyboard-only primary journey (UI 18)

Reproduced at all three tiers (out/keyboard-journey-desktop.json,
out/keyboard-journey-tablet.json, out/keyboard-journey-mobile.json): the tab order
reaches the sort control, the aging-only toggle, all inline filters (desktop) or the
Filters trigger (tablet + mobile), the inventory row/card detail trigger, opens the
detail with Enter, operates Action status -> Note -> Record action, and Escape closes
the detail. 17 focus stops (desktop) / 12 (tablet, mobile) were recorded; 0 stops lacked
a visible focus indicator. After Escape, focus is the originating
"View details for BMW X5 (1HGCR2F83HA000001)" trigger at every tier.

### 4.2 Visible focus (2.4.7)

Every keyboard-focused control renders a 2px solid rgb(37,99,235) ring with
outline-offset 2px, confirmed by :focus-visible plus the computed outline on the sort
select, aging toggle, table Details controls, pagination, the sheet Close/Done buttons,
and the detail Close and primary Record action buttons (out/focus-rings-desktop.json,
out/focus-rings-tablet.json, out/focus-rings-mobile.json, shots/focus-sort-desktop.png,
shots/focus-aging-toggle-mobile.png, shots/focus-primary-detail-desktop.png). The ring
is 5.17:1 against white and 4.90:1 against the canvas - above the 3:1 non-text requirement.

### 4.3 Detail focus entry and return

Opening the detail moves focus to the Close vehicle detail button with a visible ring at
all tiers (out/detail-entry-desktop.json, out/detail-entry-tablet.json,
out/detail-entry-mobile.json). Closing - by Escape, by the close button, and for the
direct-URL/reload path where no opener was captured - returns focus to a real control,
never body (out/detail-direct-url-focus.json, out/escape-from-control-desktop.json).
Escape also closes the detail while a select inside the form has focus.

### 4.4 Filter sheet focus behaviour (UI 13.4)

At tablet and mobile the sheet moves focus to Close filters on open, contains focus
(40 Tab and 40 Shift+Tab presses produced no escape), closes on Escape, and returns focus
to the Filters trigger (out/filter-sheet-tablet.json, out/filter-sheet-mobile.json,
shots/filter-sheet-mobile.png).

### 4.5 Accessible names, roles and semantics (UI 17.1-17.3)

- Zero unnamed interactive controls at every tier (out/unnamed-controls-desktop.json,
  out/unnamed-controls-tablet.json, out/unnamed-controls-mobile.json).
- Desktop/tablet: real table with caption "Inventory vehicles" and every th scope="col"
  (8 columns full density, 5 compact) - out/semantics-desktop.json, out/semantics-tablet.json.
- Mobile: no table; ul aria-label="Inventory vehicles" -> li -> article with a dl of
  labelled facts (out/semantics-mobile.json).
- Form: native select/textarea with real label[for] elements; filter controls are grouped
  in fieldset/legend (Vehicle / Inventory age / Status) at all tiers
  (out/filter-sheet-groups-tablet.json, out/filter-sheet-groups-mobile.json).
- Detail: role="dialog" + aria-modal="true" + an accessible name ("Vehicle detail: BMW X5")
  (out/detail-props.json).

### 4.6 Validation association (UI 14.3)

A business rejection renders role="alert" text "Vehicle veh_002 is not aging (> 90 days)"
and the form carries aria-describedby="create-action-error" pointing at that alert
(out/validation-wiring.json). The error text is 6.05:1 (out/contrast-error-390.json).
Minor observation, not a defect: the association is form-level rather than on the
individual control (#create-action-status has no aria-invalid/aria-describedby), which is
defensible because the rejection is a vehicle-level business rule, not a field error.

### 4.7 Non-colour-only communication (1.4.1)

Aging is always literal text - AGING (13px/700) or "Not aging" - and the colour dot is
aria-hidden="true" (out/noncolor.json). Lifecycle status (AVAILABLE), action status
(Legacy Hold (Discontinued), "No current action"), the current-action empty state and the
stale warning ("Inventory may be outdated. Showing the last successfully synchronized
inventory.") are all text, not colour-only. The aging legend explains the 91-day rule.

### 4.8 Contrast that passes

Measured and passing: h1 16.6:1, subtitle/secondary text 7.09-7.48:1, KPI values 17.5:1,
aging KPI label 6.68:1, aging indicator 7.09:1, table caption 7.48:1, table body 14 px
17.5:1, filter chips 6.66:1, freshness stale pill 6.68:1, primary button text 6.70:1,
form error 6.05:1 (out/contrast-dashboard-*.json, out/contrast-detail-*.json,
out/contrast2-*.json, out/contrast-error-390.json). Disabled controls (Previous page at
page 1, opacity 0.55) measure 3.94:1; inactive components are exempt from 1.4.3 and are
reported only for completeness.

### 4.9 Target sizing (2.5.8 and UI 17.12)

Every visible interactive control measured at least 24x24 CSS px at all three tiers (the
repository's AA floor), and at least 44x44 at tablet/mobile except the aging-only toggle
(F3). Removing a filter chip is 28x28 desktop / 44x44 touch; the filter sheet, its actions
and the detail controls all reached 44 px at the touch tiers (out/targets-desktop.json,
out/targets-tablet.json, out/targets-mobile.json).

### 4.10 Reduced motion (UI 19)

Under prefers-reduced-motion: reduce, all probed transitions/animations resolve to
1e-06s and the skeleton shimmer animation is not applied; the detail surface, sheet and
buttons remain fully functional (out/motion-reduced-desktop.json,
out/motion-reduced-tablet.json, out/motion-reduced-mobile.json,
out/motion-reduced-detail-desktop.json, shots/motion-reduced-mobile.png). Default motion
is functional and short (120 ms background/colour transitions).

### 4.11 Responsive surface geometry and overflow (UI 11, 21)

Drawer/sheet/fullscreen geometry matches the tier exactly: desktop drawer 544 px pinned
right (1280x800); tablet sheet 767 px centred with 5 vh insets (834x1112); mobile
fullscreen 390x844 (out/detail-geometry-desktop.json, out/detail-geometry-tablet.json,
out/detail-geometry-mobile.json). No horizontal page overflow at any tier
(out/overflow-desktop.json, out/overflow-tablet.json, out/overflow-mobile.json). The
sticky table header did not obscure a focused row control (2.4.11) at desktop or tablet
(out/focus-not-obscured-desktop.json, out/focus-not-obscured-tablet.json).

## 7. Limits

Automated plus keyboard/browser verification cannot fully judge screen-reader
announcement quality; no NVDA/VoiceOver pass was performed. Motion was verified via
computed styles under emulated prefers-reduced-motion, not by observing animation frames.
Contrast was computed for sampled representative elements per region; the token-level
root cause of F2 makes the failure general wherever --ui-text-muted is used.
