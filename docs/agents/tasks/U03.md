## 2. Semantic token and CSS architecture

### 2.1 Where tokens live

Add a global style layer inside an already-scanned production root:

```
src/app/styles/tokens.css     # @layer order + primitive tokens + semantic tokens
src/app/styles/base.css       # minimal reset, base typography, global :focus-visible, reduced-motion
src/app/styles/primitives.css # shared primitives: .ui-button, .ui-chip, .ui-panel, .ui-status-pill, .ui-vlabel, .ui-sr-only
```

`tokens.css` declares the layer order once, on the first line:

```css
@layer tokens, base, primitives, components;
```

Primitive tokens carry raw scales (`--ui-space-4`, `--ui-radius-8`, `--ui-color-slate-900`);
semantic tokens carry decisions and are the only values components may consume:

```css
@layer tokens {
  :root {
    --ui-canvas:#F6F8FB; --ui-surface:#FFFFFF; --ui-surface-muted:#F1F5F9;
    --ui-text-primary:#0F172A; --ui-text-secondary:#475569; --ui-border:#D8E0EA;
    --ui-interactive:#1D4ED8; --ui-interactive-hover:#1E40AF; --ui-focus:#2563EB;
    --ui-aging-text:#9A3412; --ui-aging-bg:#FFF7ED; --ui-aging-border:#FDBA74;
    --ui-success-text:#166534; --ui-success-bg:#F0FDF4;
    --ui-error-text:#B42318; --ui-error-bg:#FEF3F2;
    /* type scale, spacing rhythm, radius, elevation, motion, z-index layers */
  }
}
```

Values match UI System Design §8. Feature stylesheets wrap their rules in
`@layer components { … }` and reference only semantic tokens. A component-level token is
added only when a semantic token genuinely cannot express the mapping (skill token rule).

### 2.2 How they are imported (Vite + jsdom safety)

- Import order in `src/main.tsx`, **before** `./app/App`:
  `import './app/styles/tokens.css'; import './app/styles/base.css'; import './app/styles/primitives.css';`
- Vite bundles CSS from side-effect imports exactly as it already does for
  `inventory-dashboard.css` / `vehicle-detail.css`; nothing in the build changes.
- The Vitest config (`vitest.config.ts`) sets no `css` option, so CSS is not applied inside
  jsdom. CSS side-effect imports are already used by production components without
  affecting the jsdom suite, so token imports cannot break it either.
- The one test that reads CSS does so with `fs.readFileSync` on `vehicle-detail.css`
  (`vehicle-detail.test.tsx:112`), so token placement is irrelevant to it.
- No token needs to be imported by a `.ts`/`.tsx` module, so the architecture AST checks
  (which only scan `.ts`/`.tsx`) are unaffected.
- `@layer` makes the cascade independent of bundle order, so a feature stylesheet never
  depends on tokens.css being emitted first. Add `var(--ui-…, <fallback>)` only for the
  handful of tokens used in a file that could conceivably render without the token layer.
- Do **not** create `src/styles/…` or any top-level `styles/` sibling of `app|api|features`;
  `src/app/styles/` keeps everything inside a production root that the architecture proof
  already knows about. (CSS is not AST-scanned, so this is convention, not a hard gate.)

### 2.3 Replace the inline route shell

`src/app/router.tsx` renders `<div style={{ padding:'2rem', fontFamily:'system-ui, sans-serif' }}>`.
Move this to a class (e.g. `.app-shell`) in `base.css`; the dashboard supplies its own
centred content container. Keep the index-route strings (see `contracts.md`).

## 6. Required analysis items

### 6.1 TanStack Table v9 can carry the redesigned desktop and tablet semantics — yes
`vehicle-table.tsx` uses the v9 headless API (`useTable`, `tableFeatures({ rowPaginationFeature })`)
and renders the DOM itself: `<table><caption><thead><th scope="col">…<tbody><tr><td>` with
`table.FlexRender`. All visual work is therefore CSS/class work on existing semantic output;
the headless model imposes no styling limit. Constraints that must hold:
`manualPagination: true` + `rowCount` + `data-density` stay; no `rowSortingFeature` /
`columnFilteringFeature` is registered and `manualSorting` is never `false`
(`architecture.test.ts` rejects all three); the column set and header text are frozen because
both suites assert exact header arrays (see `contracts.md`). Sticky header, column priority,
zebra/hover rows and truncation are pure CSS on the existing markup.

### 6.2 Mobile keeps list/article semantics and never renders a table
`VehicleCards` renders one named list (`<ul aria-label="Inventory vehicles">` → `<li>`),
selected by `useViewportTier()` and never co-rendered with the table. Keep the list + item
semantics; an `<article>` inside each `<li>` is allowed and matches UI §17.3. Do not fake a
grid with `<table role="presentation">`: `e2e/responsive-presentation.spec.ts` asserts
`page.locator('table')` has count 0 on mobile and the unit suite asserts `queryByRole('table')`
is null.

### 6.3 Touch targets: the 44px design requirement vs the asserted 24px floor
UI System Design §8 requires **44 × 44 CSS px** for touch-oriented controls, "unless a dense
desktop-only table uses an equivalent accessible target". `e2e/accessibility.spec.ts`
enforces **24 × 24** (WCAG 2.2 SC 2.5.8 AA) for every visible
`button | a[href] | select | textarea | input:not([type=hidden])` in the page, the filter
sheet and the detail. Reconciliation:

- 24px is the **enforced floor** everywhere a control is measured; never go below it.
- 44px is the **design target** for touch-oriented controls: all controls rendered at the
  tablet and mobile tiers (`hasTouch` projects) get `min-height/min-width: 44px` (or a 44px
  hit area around a smaller visual glyph).
- The dense desktop table is the documented exception: its inline controls may use the 24px
  floor, backed by a full-row hover/focus affordance and adequate row height.
- Because the e2e measures the tablet/mobile table and sheet controls too, the 44px target is
  what makes those projects pass comfortably rather than marginally.

### 6.4 focus-visible styling satisfies the focus assertion
`e2e/accessibility.spec.ts` requires, for a focused element, `el.matches(':focus-visible')`
**and** either (`outline-style !== 'none'` and `outline-width >= 1px`) **or**
`box-shadow !== 'none'`. Relying on UA defaults is fragile, so `base.css` defines it
explicitly:

```css
:where(a, button, input, select, textarea, [tabindex]):focus-visible {
  outline: 2px solid var(--ui-focus);
  outline-offset: 2px;
}
```

2px ≥ 1px, `outline-style: solid`, so both branches agree. Any box-shadow ring alternative must
also be ≥1px-visible and not hidden by `overflow: hidden`/`overflow-y: auto` ancestors; the
drawer/sheet and sheet scroll areas therefore keep interior padding (and/or use the outline ring
rather than an inset shadow) so focus rings near the edge are not clipped.

### 6.5 Reduced-motion support
`base.css` ends with a single global guard so it also covers future animated rules:

```css
@media (prefers-reduced-motion: reduce) {
  *, *::before, *::after {
    animation-duration: .001ms !important;
    animation-iteration-count: 1 !important;
    transition-duration: .001ms !important;
    scroll-behavior: auto !important;
  }
}
```

This is the intentional, documented use of `!important` the skill allows for a reduced-motion
override. The skeleton shimmer is additionally defined inside
`@media (prefers-reduced-motion: no-preference)` so the reduced state is a static muted bar.
All other motion stays functional and within 120–220ms (UI §19).

### 6.6 Avoiding generic template/SaaS defaults (concrete, not adjectives)
- **Type scale** (explicit, not "larger/smaller"): 12 / 13 / 14 / 16 / 20 / 26 / 32px with
  matched line-heights (1.2 titles, 1.45 body, 1 for numerals); KPI values use the largest
  step with `font-variant-numeric: tabular-nums`; KPI labels and table headers are 12px
  uppercase with `letter-spacing: .04em`.
- **Spacing rhythm**: only the scale tokens 4 / 8 / 12 / 16 / 24 / 32 / 48; section gaps 24–32,
  intra-card gaps 8–12, control padding 8–12. No arbitrary rem values.
- **Surface hierarchy**: exactly four levels (canvas → panel → raised/interactive → semantic
  status) separated by **border/contrast first**, with elevation reserved for drawer/sheet/
  menu/overlay (UI §7.2/§7.3).
- **Semantic color**: aging = amber token family; lifecycle/action = neutral pill with text;
  success green only for genuinely healthy states; red only for errors. No gradients, no
  glassmorphism, no oversized uniformly-rounded cards, no decorative charts.
- **Distinct signature**: the operational header (identity + freshness) and the aging emphasis
  treatment are the product's visual signature; consistency elsewhere stays deliberately calm.

The repository Playwright suite remains the deterministic gate; this is exploratory evidence.

## 10. Paths likely to overlap (concurrency and review risk)

| Overlap | Files | Risk / mitigation |
|---|---|---|
| Token layer consumed by both features | new `src/app/styles/*`, `inventory-dashboard.css`, `vehicle-detail.css` | single global token file is a shared seam; land it first, then restyle features |
| Shared primitives | new `src/app/ui/*` imported by `features/inventory/**` and `features/actions/**` | both features depend on the primitive API; freeze it before styling either feature |

| Test-coupled CSS | `vehicle-detail.css` (read by `vehicle-detail.test.tsx`) | literal rules are asserted; a redesign of the file must preserve the exact rule bodies |

Because a single implementation task owns all of these, U03 is one serialized writer with no
parallel sibling. Vertical slicing would create overlapping CSS/token seams.
